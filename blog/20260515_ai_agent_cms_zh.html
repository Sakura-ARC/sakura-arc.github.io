比起发SNS，让AI更新自建站更轻松！—— Antigravity × GitHub Pages 架构讲座

前言：为什么这个博客既没有用 Note 也没有用 WordPress

这篇文章，其实是我只在聊天窗口里下达了指令就写出来的。AI 构思了文章结构、生成了 HTML，并直接推送（Push）到 GitHub 完成了发布。我所做的，仅仅是“传达写作大方向”和“对最终产物进行确认”而已。

为什么我既没有用 Note、WordPress，也没有用 X（旧 Twitter），而是选择在这样一个静态网站上开设博客？答案很简单：在拥有了 AI 代理（AI Agent）的今天，让 AI 帮我更新自建站，远比在社交媒体（SNS）上绞尽脑汁发帖要轻松得多。而且，自建站上的内容会作为地道且实打实的 SEO 资产不断累积，这虽然是个不起眼的低调策略，却有着极高的潜在价值。

【体验】SNS 投稿的“疲惫感”与 AI 代理的引入

站在 2026 年的今天，利用 AI 编写代码或起草文章已经不是什么新鲜事了。只要打开 ChatGPT 或 Claude 之类的网页版应用，任何人都能轻松获得像模像样的成果。

然而，对于没有任何 IT 经验的个人开发者来说，最大的障碍并不是 AI 给出的“回答”本身，而是在将这些回答反映到自己项目里时所产生的巨大“摩擦力”。

回顾 2025 年左右，在 VSCode 中使用 GitHub Copilot 或 Gemini 的环境已经非常成熟。即便是在 Ren'Py 这样的游戏引擎中，AI 自动推荐下一行代码的体验也确实很方便。

但那终究只是“编辑器内部的辅助”而已。新建文件、复制粘贴 AI 的回答、保存、用 Git 管理、再手动发布。这种“AI 网页与本地文件”之间看不见的壁垒，对于 IT 门外汉来说依然高不可攀，且极其繁琐。

转机发生在 2026 年的 2 月到 3 月期间。当时为了撰写参加早川 SF 大赛的小说，我尝试将 AI 代理“Antigravity”引入到了我的项目仓库中。

那时我切身体会到了网页版 AI 绝不可能拥有的“上下文（Context）保持能力”。我不需要每次都繁琐地把历史资料复制粘贴喂给它，AI 也绝对不会迷失项目的整体结构。它在我的仓库里自由穿梭、读取资料、更新大纲。

“AI 能在我的本地电脑里，噼里啪啦地读取、创建、更新各种资料和脚本，这种感觉真的很棒。虽然稍微有点让人害怕，哈哈。”

更具革命性的一点是，这个 AI 代理可以“像人类一样操作浏览器（Chrome）”。它不仅能在网上搜索，必要时还会亲自启动浏览器、访问网站、提取信息并将其整合到项目中。这是网页版 AI 无法企及的领域，也是拥有“手脚”的 AI 代理所特有的降维打击能力。

当然，这并不是说它是一个能够解决所有问题的“魔法”。AI 的上下文保持依然存在物理局限，人类在适当时机给出正确引导、喂给它合适参考资料的“驾驭能力”仍不可或缺。我个人也会根据具体任务，将网页版 AI 和 NotebookLM 等各种工具打散配合使用。

但是，自从将 Antigravity 置于项目的核心位置后，以往在无意义的“复制粘贴”上消耗的庞大时间，被彻底转化为了更有价值的、高层次的创意性试错。

【发现】自建站更新比 SNS 更“轻松”的逆转现象

小说投稿结束后，我把开发重心转回了正在制作的悬疑游戏《神屋侦探事务所》项目中。在这里，又一次颠覆性的体验正等待着我。

通常，大家做独立游戏宣传时，主流选择都是 Note 或 X（旧 Twitter）。但对于不擅长长篇大论的我来说，面对外部平台的发布窗口，手动把 AI 的回答复制粘贴并进行排版，是一件相当消耗精力的累人工作。

但在“Antigravity ✕ GitHub Pages”的环境下呢？我只需要在聊天框里敲下一句：“把这次开发的感悟整理成一篇文章，用平时的模板发布一下。”AI 就会直接生成 HTML、整理好目录结构、提交并推送，让它瞬间公开在互联网上。

“比起把内容复制粘贴到外部 SNS，直接让 AI 更新自己的网站要省力得多。” 这是一种此前难以想象的、“费力程度”的彻底逆转。

【本质】为什么 GitHub Pages ✕ AI 是“理想的发布底座”

为什么现在要极力推崇 GitHub Pages？因为这个平台的“极简性”，与 AI 代理的天然属性产生了完美的化学反应。

如果试图让 AI 去管理传统的服务器主机或复杂的 CMS（比如 WordPress），就会遇到登录、填写表单、管理数据库、FTP 传输等一系列繁杂且脆弱的步骤。这些系统是专为“人类使用浏览器进行视觉化操作”而设计的。对 AI 而言，它们笨拙、易错且极其容易被搞崩溃。

而在 GitHub Pages 中，所谓的“发布”动作，被高度浓缩为了唯一的一个动作：“Git push”。

创建文件、放入文件夹、提交并推送。对于 AI 代理来说，这只是它最擅长且最基础的“文件操作”的自然延伸。当操作的抽象度被提升到极致后，对 AI 而言，“修改仓库代码”变成了一种远比“敲击管理后台”更安全、更快速、更鲁棒的部署手段。

作为项目拥有者的我们，所需要做的仅仅是在聊天框里下达一句指令：“更新这篇文章。”AI 就会在幕后完成撰写、处理素材、格式化 HTML 并完成推送。曾经被视为累赘日常的“博客维护”动作，悄无声息地从我们的意识中彻底淡出。这就是 AI 代理 ✕ GitHub Pages 所带来的、个人开发最理想的发布底座的真实面貌。

当然，这也并非万无一失。例如在处理 Steam 商店的 18 国语言本地化时，即便我用 JSON 备齐了所有主数据，但面对商店后台庞大且琐碎的 UI 输入项，最终依然演变成了一场令人窒息的“复制粘贴地狱”。或许 Antigravity 的浏览器操作功能以后可以实现全自动化，但面对一旦出错就可能导致灾难性后果的商店核心设置，目前让 AI 全权接管依然会觉得“害怕”……这种人类心理上的踩刹车，也是目前最真实的开发写照。

【SEO】自建站内容将作为“长期资产”不断累积

此外，在自建的静态网站上运营博客，还隐藏着一个深层次的战略意图：自建站的内容，会直接作为你个人的 SEO 资产被永久留存并不断升值。

发布在 Note 或 X 上的内容，其生杀大权完全掌握在第三方平台手中。算法一变，你的曝光度可能瞬间归零；服务一旦关停，你多年的心血将化为乌有。然而，在你自己域名下积累起来的内容，随着时间的推移，在 Google 眼中的权重会越来越高，成为一个稳定、长效的自然搜索流量入口。

这篇文章本身，就是这个实验的第一步。通过“AI 代理”、“GitHub Pages”、“个人开发”等关键词，逐步在搜索结果中崭露头角……这是一种虽然低调、但绝对稳健的复利累积策略。关于如何通过 Steam 审核、以及我们 18 国语言本地化的硬核技术细节，我会在后续的文章中深入展开。

【结论】AI 正在向“项目共建者”演进

没有任何 IT 专业知识的我，却能制作出支持 18 国语言的游戏、并在极短时间内搭建出高水准的现代网站。这一切之所以能够实现，是因为我不仅把 AI 当作“助手”，而是将其视为了一个能够共享项目上下文、并代为执行实务的“最强共建合伙人”。

诚然，让 AI 在自己的本地电脑里自由操作文件，确实存在风险和令人敬畏的一面。人类必须通过版本控制、离线备份等手段牢牢握住“缰绳”。但这种协作模式所带来的无可比拟的爆发式开发速度，足以弥补所有的不安。

技术的壁垒已经被 AI 彻底击碎。现在，我唯一需要专注的，仅仅是“接下来要做什么才更有趣”这一核心决策。如果你已经对和 AI 之间无休止的“复制粘贴”感到厌烦，或者因为自己是“IT 小白”而犹豫不决，我强烈建议你立刻把一个 AI 代理请进你的仓库。在前方等待着你的，将是一个远比想象中更自由、且“不再孤单”的个人开发新纪元。

“不过，如果太依赖 AI 的话，说不定反而会以另一种形式感到孤独呢，笑。”
